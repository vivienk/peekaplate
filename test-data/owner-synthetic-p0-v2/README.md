## 1. Project Overview

This package contains fictional synthetic event data for testing PeekaPlate's owner-facing metrics, event validation, privacy suppression, Save behavior, engagement calculations, and AI assistant grounding.

The dataset is intended for local evaluation and independent review.

**Important limitations:**
- This is not production customer data.
- It is not approved for production database import.
- Passing local tests does not prove production integration correctness.
- AI evaluation cases have not been executed against the application.
- Metric definitions and certain product decisions still require approval.

## 2. Dataset Overview

The package includes two synthetic datasets.

| Dataset | Sessions | Delivery Lines | Unique Events |
|---|---:|---:|---:|
| Two-session starter fixture | 2 | 21 | 20 |
| Full replicated fixture | 300 | 3,150 | 3,000 |

The full dataset is generated by repeating the two-session story 150 times.

It includes 150 identical retry deliveries for deduplication testing.

**Synthetic observation window:** October 20, 2026, 10:00:00 through 11:00:07 (UTC+05:00), including both endpoints.

These sessions are fictional replications and must not be interpreted as 300 independent real customers.

The repeated story is not suitable for establishing real customer trends or growth.

## 8. Engagement Metric Examples

Six event-derived examples are included in `metric_examples.json`.

They cover:

1. Active-time-only engagement.
2. Qualifying displayed comparison with a linked opening.
3. Short opening without qualifying engagement.
4. Save-only activity.
5. Exactly 10 seconds of active visible time.
6. Displayed comparison without a linked opening.

The proposed considered-dish rule requires either:

- At least 10 seconds of active visible time; or
- A qualifying displayed comparison associated with the appropriate opening.

Activity checkpoints represent cumulative active time and must not be added together as independent durations.

A Save event alone does not establish considered-dish engagement.

**Unresolved product decision:** Whether a displayed comparison qualifies both participating dishes or only the dish associated with its linked opening.

Under the current provisional interpretation, the full synthetic dataset produces:

- Dish A: 150 qualifying opening sessions out of 150.
- Dish B: 0 qualifying opening sessions out of 150.

Dish B's result must remain provisional until comparison attribution is approved.

## 9. Saved State and Finalized Retention

Story-end Saved state and finalized retention are different measurements.

### Story-end Saved state

The original two-session story ends with:

- Session X: Dish A saved.
- Session Y: No dishes saved.

These are fixture-end Saved-state assertions, not verified completed-session retention.

### Finalized retention

The proposed retention policy uses:

**Numerator:** Completed sessions that directly saved the dish and still have it Saved at completion.

**Denominator:** Completed sessions that directly saved that dish.

The calculation excludes:

- Unfinished sessions.
- Completed sessions that never directly saved the dish.

When the denominator is zero, the retention rate is `null`.

Standalone automated examples cover retained savers, completed savers who no longer retain the dish, and cases with no eligible completed savers.

The main synthetic dataset does not independently establish session completion.

An explicit completion event or approved inactivity-timeout rule is required before finalized retention can be calculated from application data.

AI-facing reports must not expose private diner event histories, raw event IDs, session IDs, checkpoint histories, or individual Saved lists.

Suppressed metrics must not reveal hidden values, including through inferred counts or denominators.

The test oracle containing expected facts and forbidden claims must remain separate from the AI-facing input reports.

Automated checks cover fixture existence, JSON readability, suppressed metric values, prohibited private field names, and execution statuses.

These structural checks do not establish complete privacy compliance or correct application-AI behavior.

No application-AI scores or pass rates are claimed.

## 11. Privacy and Reporting Limitations

The proposed minimum reporting threshold is **10 eligible sessions**.

Behavioral metrics below the threshold must be suppressed in owner-facing output.

For suppressed values, an AI-facing report should use a structure such as:

```json
{
  "metric": "dish_openings",
  "status": "SUPPRESSED",
  "value": null
}
```

The suppressed value must not be replaced with the hidden count.

Privacy testing must also consider:

- Cross-restaurant data access.
- Inference of suppressed values.
- Complementary suppression.
- Unauthorized raw-event access.
- Unsupported customer-behavior claims.

Passing synthetic fixture tests does not establish production tenant isolation or privacy compliance.

## AI Evaluation Input Boundary

The 20 AI evaluation cases are defined in `ai_evaluation_cases.json`.

For each future application-AI evaluation, the model may receive only:

1. The case's `question`.
2. The authorized, privacy-filtered fixture referenced by `input_fixture`.

The model must NOT receive:

- Expected answers, expected behavior, or grading criteria.
- Private test facts or hidden evaluation notes.
- Raw event records or unsuppressed behavioral counts.
- Data belonging to another restaurant.

The `permitted_inputs` field describes the authorized evidence available through the referenced fixture. It does not authorize additional data access.

Expected answers and grading criteria are reserved for the evaluator, not the model.

Suppressed metrics must remain suppressed. The model must not infer hidden counts, Save rates, or dish rankings from suppressed values.

All 20 cases remain NOT RUN against the application AI. Passing local fixture tests does not establish application-AI performance.
