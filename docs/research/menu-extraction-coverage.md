# Menu extraction: coverage, fidelity, and release gate

2026-11-18. Decision: use V4 + coverage-only as the development candidate; keep the deployed/default prompt unchanged until the candidate passes a source-reviewed comparison against the intended merge base. No new model generations were made for this research.

## Evidence and branch mismatch

- In the private November 18 comparison, the two coverage variants each returned 76 candidates on the dense development page versus 42 from standard V4. Source spot-checks confirmed real dishes and printed prices among the extra rows. Coverage-only recovered five separately printed add-ons on the second menu; identical calamari labels and prices actually belonged to different salads. It also misfiled two side items on the first menu. Neither menu is held out and the spot-check is not an exhaustive accuracy score.
- The three-arm trial was partial because one diagnostic-arm page lost its connection. Coverage-only was a separate successful follow-up, so small count differences between coverage variants cannot isolate the effect of the diagnostic wording.
- The [merged extraction handoff](https://github.com/vivienk/peekaplate/pull/58) does not establish that the trial code landed. On the November 18 GitHub check, `main` and `develop` had the baseline prompt assembly in `processing/src/peekaplate_processing/vision_extraction.py`; `main` constructed drafts with `ingredients=None`. The coverage-only trial ran against a local ingredient-aware worktree with structured response format configured, not this merge base. The previous patch check applies to that local worktree only. A prompt-only PR against upstream cannot make the draft export ingredients if the producer still drops the field.
- Google [structured output](https://ai.google.dev/gemini-api/docs/structured-output) constrains JSON shape, not extraction truth. The schema did not vary in the trial; it was not evaluated as a treatment.

## What to improve, in order

**First, score the saved runs offline.** Have a reviewer transcribe the three inspected pages without seeing predictions, then separately associate the saved baseline and coverage-only candidates with those source rows. Keep these development scores separate from holdout scores. This determines whether the added candidates are correct and where to spend the next provider calls.

The [strict scorer operator guide](../../processing/eval/qa02/STRICT_SCORER.md) specifies the private frozen manifest, one `qa02.runs.v1` ledger per condition, and independently reviewed candidate-to-occurrence associations. The November 18 checkout inspection found no independently reviewed frozen real-menu reference or compatible scored receipt. Scorer exit 0 means the receipt was computed, not that extraction passed.

1. **Establish a source-reviewed reference.** Keep the two inspected menus as development fixtures. Independently label unseen, permitted examples spanning a dense digital PDF, image-only PDF, and phone photo; include price variants, repeated names, printed add-ons, and description lines. Label by printed occurrence and page, not by normalized title. Freeze references and release thresholds before fresh predictions. Reuse [QA-02](../qa02-real-menu-source-plan-v1.md), [merged reference protocol #169](https://github.com/vivienk/peekaplate/pull/169), and the [strict scorer work #181](https://github.com/vivienk/peekaplate/pull/181): name precision/recall, complete price text/group plus nullable scalar and currency, and failure-inclusive denominators. The existing scorer is not proof of description or ingredient quality: separately review verbatim descriptions and ingredient facts, keyed to the same occurrence; include missing, invented, negated, optional and wrong-item terms. Verify the accepted field survives the draft → review export path. Do not infer an unprinted recipe or allergy status.
2. **Compare baseline and candidate on the same code and inputs.** Pin the production-target revision, model, schema, page bytes and settings. Isolate the ingredient handoff from the prompt change, then compare baseline vs. coverage-only on the same extractor. Record complete versus partial responses, truncation, latency, and attempted calls. Open a narrow prompt PR when the agreed thresholds pass with no unacceptable regression in prices, descriptions, or ingredient precision. Run the frozen offline scorer on saved artifacts; live trials need their own approved call budget.
3. **Improve source readability before adding more prompt prose.** Test layout-preserving native PDF text plus the page image in the same request for digital PDFs; don't treat faulty text order as source truth. For scanned/image-only pages, test dense-column crops or clearer rendering with page/region identity preserved. Compare native Gemini PDF input or explicit visual resolution as separate experiments; Google documents [PDF understanding](https://ai.google.dev/gemini-api/docs/document-processing), [media resolution](https://ai.google.dev/gemini-api/docs/media-resolution), and the [OpenAI-compatible surface](https://ai.google.dev/gemini-api/docs/openai) separately. Per-item native settings are not assumed to work through the compatibility endpoint, and documented default image token allocation already matches `high` for Gemini 3. Image tiling or repair calls must fit the [hosted two-attempt job budget](../provider-call-budget.md); no routine second pass per page.
4. **Validate against independent evidence.** Flag unreadable pages, missing visible sections, incomplete member/non-member or size price groups, and implausible descriptions. An emitted candidate's model-derived `source_text` is not independent evidence. Compare against the original PDF text or independently sourced OCR/layout evidence where reliable; surface disagreements to review. Preserve repeated add-ons under different parents; don't deduplicate on name, price, and category alone. If parent identity cannot be established from source evidence, flag it rather than guessing.

Maintenance: run the frozen comparison whenever the model, prompt, schema or renderer changes. Review score drift and stale run assumptions before making another production change. Keep originals, private labels, telemetry and exports out of GitHub.

## Execution handoff

- [Source review](https://app.clickup.com/t/86bd3h93x#comment-90140283185690): privately give the independent reviewer the three original pages and draft worksheets, not predictions. Record corrections and sign-off before freezing. Keep unconfirmed parent links and ingredient boundaries explicit; do not promote either development menu to holdout.
- [Saved-run scoring](https://app.clickup.com/t/86bd4v796): freeze the reviewed reference, then record separately reviewed candidate-to-occurrence associations for each condition. The four report/export pairs already passed the source-hash and exact re-export preflight. Run the strict scorer and attach a sanitized comparison; show add-on, description and ingredient judgments separately where the scorer cannot represent them.
- [Held-out comparison and PR decision](https://app.clickup.com/t/86bd4v79g): qualify the two proposed PDF sources and a permitted, previously unseen photo. Freeze independently reviewed references and agreed thresholds, verify the ingredient handoff on the pinned target revision, and record an approved call budget before generating. Compare standard and coverage-only with every other setting fixed; keep failed pages in the result. Open a narrow prompt PR only after the agreed gate passes. No live execution or production acceptance is implied by this checklist.
