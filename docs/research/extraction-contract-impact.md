## What changes what

| Proposed change | Contract decision |
| --- | --- |
| Coverage-only wording; remove redundant Unicode regex flag; reject unsupported negated/optional ingredient proposals | No shared shape or migration needed. Prompt and value behavior change for **new** runs. Preserve `ingredients: null` when unsupported and do not imply OCR, approval, or allergen verification. |
| Local ingredient-aware V4 work | **The provider-facing `V4Dish` JSON schema does change**: it adds `ingredients` and submits a strict Google response format. Neither shared `DishDraft.ingredients` nor `candidates[].original.ingredients` is new. Descriptions add real data and a second evidence span to the producer output; this is a semantic/payload change on existing keys, not a transport version bump. Verify the existing consumers with an actual exported payload. |
| Retain completed pages on budget denial or later-page failure | Existing `incomplete` report/job, page statuses, errors and warnings are sufficient. Preserve already valid candidates, mark remaining pages, and test bootstrap and save/reload. Do not return new fallback outcomes or change 429/504 transport, budget, retry, lease or archival semantics without Teeyansh. Keep the two-attempt cap. Full support for accepted 3–10-page documents cannot come from partial preservation alone: agree batching or an explicit intake/coverage policy first. |
| Require exact ordered newline reconstruction and exact one-to-one evidence matching | No new fields, but **stricter acceptance semantics** at Teeyansh’s boundary. Reject only after auditing legacy v1/v2 and v2/v3 fixtures, optional/null behavior, historical artifacts and exact draft matching. Check acceptance, invalid-row diagnostics, partial persistence and Marwan’s review bootstrap together. Do not rewrite stored originals or supply fabricated joins. |
| Align Unicode field length | Align Python/TS code-point rules without changing the stated cap; keep UTF-16 conversion where JS needs it. Shared validator behavior changes, so test both directions and keep old fixtures valid. |
| Show model provenance and approximate geometry | Existing candidate evidence, `metadata.text_origin`, `metadata.vision_boxes` and approved source delivery can support a display change. Verify authorized image access, page transform and pixel bounds; if no compatible image is served, show the provenance text without pretending to show a region. Do not copy vision boxes into OCR box fields, add an unreviewed endpoint or expose local paths. |
| Preserve full over-limit price literal for review | Keep the existing 160-character field cap, leave bounded price fields unknown and retain the warning. A full literal in existing producer-bound evidence is possible, but changes text reconstruction, size and new-run draft hashes. Agree the display/provenance and storage behavior with both owners before adding a new metadata convention or widening the field. Never edit an existing artifact or force an option group into Bundle v1’s scalar. |
| Structured price-option arrays, parent-add-on relations, new evidence roles or public fields | Not part of the reviewed change. These would extend cross-layer semantics and require explicit version/consumer agreement. Bundle v1, publication policy and DB schema remain untouched. |

## Before changing code

1. Pin the feature integration branch to `develop` and bring over only the intended producer changes; the dirty donor is not a release branch. Preserve format/version pairs, private Option 3 envelope, source identity and prior immutable attempts/review sessions. Draft IDs are content-derived in the donor, so newly extracted values can change IDs in a **new run**; do not promise cross-run ID stability or recompute IDs on reviewer corrections.
2. Fix partial-page loss and literal ingredient matching first. Then prove `source → report → hosted V1 → adapter → review bootstrap → correct/save/reload` across both version pairs with a valid partial case, Unicode boundaries, repeated titles/add-ons, grouped prices and unknown ingredients. A three-page run under the unchanged cap should preserve the first two successful pages and mark the third unread, not claim completion. Separately agree how to support all pages for accepted larger menus.
3. Coordinate stricter adapter rules, provenance display and overlong-price evidence with the owners before rollout. `backend/src/ingestion/review-bootstrap.ts` bounds serialized review payloads to 524,288 bytes. The saved compact exports were 107,963 → 157,904 bytes (Panania) and 82,913 → 93,093 (Twin City), baseline to coverage-only; these are artifact measurements, not hosted-cap acceptance. Test a dense near-limit case before adding repeated evidence text, without lifting a documented cap silently.
4. Do not alter Bundle v1. Keep approval and publication separate. Review parity and staging behavior should be asserted whenever the producer schema, renderer or mode changes, not inferred from a PR merge or isolated offline tests.
