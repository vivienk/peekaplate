# Production release during the Meta freeze

Use a reviewed exact commit from the official repository's **develop** branch for a manual production release during the freeze. This is a proposed exception to the source-branch rule in [ADR 0012](adr/0012-main-environment-promotion.md). Keep its independent release sign-off and separate environment boundaries. Do not deploy to the existing Meta staging projects or update main. Inspect the exact candidate in an isolated environment before domain cutover.

Check the existing Cloudflare DNS and HTTPS rules before attaching custom domains. Preserve existing mail DNS and the .io site. Do not copy staging's Hyperdrive ID or point production extraction at its R2 bucket or Queue. Provision a dedicated production Supabase database and restricted runtime login/Hyperdrive. Apply the reviewed migrations to that database. Use the existing empty production R2 bucket after verifying its private access settings. Bind the separate production queues and DLQs using [the API config](../backend/wrangler.production.jsonc). Both primary queues should stay paused until the first bounded production acceptance window.

## Build and release

1. Record the candidate SHA, passing CI and independent end-to-end evidence. Test a fresh database and a rollback before any production traffic. Reject candidate builds that use a staging origin, demo or fixture mode.
2. Configure the exact production Supabase callback URLs at `https://peekaplate.app/auth-confirm.html` and `https://peekaplate.app/auth-reset.html`. The callback also accepts Pages' clean URLs. Configure the approved production email sender. Keep only the public Supabase URL and publishable key in the console build. Set `VITE_OWNER_AUTH_ENABLED=true` and `VITE_PUBLIC_API_URL=https://api.peekaplate.app` there.
3. For diner, set `VITE_MENU_SOURCE=live` and `VITE_PUBLIC_API_URL=https://api.peekaplate.app`. Build with `pnpm --filter @peekaplate/diner exec vite build --base=/diner/` and use `pnpm prepare:app-site --diner frontend/diner/dist --output NEW_OUTPUT_DIR` for explicit slug and legacy QR routes. Set an `/ /owner-auth 302` rule in the production console build's `_redirects`. Use the existing S13 preview and publish components.
4. Check `wrangler deploy --dry-run --config wrangler.production.jsonc` and the [extraction configuration](../backend/wrangler.extraction.production.jsonc) from the backend directory. Provide the dedicated Hyperdrive ID, database auth issuer, menu-signing JWK and unique extraction service and source-signing secrets through approved operator channels. Provider configuration remains private. Do not enable `OWNER_WORKFLOW_ENABLED` or `EXTRACTION_PRODUCTION_ENABLED` before the corresponding bindings are verified. Do not enable production analytics or AI by copying staging settings.
5. Deploy the exact verified SHA, with explicit production project names and code hashes. Verify first signup confirmation and sign-in, S05 profile creation, OCR, review, S13 preview/publish, diner link load and withdrawal, and authorized observation delivery. Use two different signed-in restaurant owners and publication links to check isolation. Check the actual deployed asset references and confirm the prior release still works before moving DNS. Record deploy IDs and the rollback target.

Exercise S09 generation and approval on the five-dish QA restaurant, republish via S13, and confirm the same public diner URL renders the revision-bound portion after reload.

## Tracking and reporting boundary

The additive diner events keep `dish_activity_checkpoint` for elapsed time, use `dish_portion_opened` only when a portion renders, and retain `dish_compared` for displayed comparison evidence. A result can render the anchor and two other dishes. Pair rows share a comparison ID, so count distinct IDs to measure completed Compare actions. The canonical ingest route derives venue and publication from its signed menu token. It does not use a browser venue field or a PostHog project ID as tenant authority.

Standalone published menu pages on the production diner origin automatically send supported interactions to canonical ingestion and configured PostHog. The embedded Screen 13 phone preview sends no events. The production diner has no consent prompt. The browser’s Do Not Track and Global Privacy Control signals stop both destinations. Staging retains its existing opt-in. Diner activity uses randomly generated identifiers and does not include names, emails or account IDs. Verify the public privacy disclosure before activating the production build. Production captures may use the resolver’s public venue and publication IDs for internal filtering. Canonical ingestion checks the signed tenant and publication. A supplied dish/revision pair still needs to be checked against that publication’s verified manifest before owner metrics can use it. The owner reporting and AI data-source change needs a reviewed extension to [ADR 0013](adr/0013-posthog-export-boundary.md) and [ADR 0003](adr/0003-intent-evidence.md) before production activation.

For live and historical reporting, validate event identity, tenant, publication, occurrence time and cohort before exposing metrics. Use the same privacy floor and metric definitions through the existing chart and AI contracts. Test late arrivals, the half-open UTC cutoff and replay. Leave the frozen staging export unchanged. AI must use the same authorized window and freshness as the dashboard and abstain on unknown evidence.

The [production report proposal](adr/0017-production-owner-report-sources.md) uses the canonical Queue and Supabase history without exposing or depending on the optional PostHog export. The new production route is disabled by default. For approved activation use the existing production Worker and a query-scoped key for the designated US PostHog project in `POSTHOG_OWNER_REPORT_READ_KEY`, with its numeric `POSTHOG_PROJECT_ID`. Do not use a browser capture token for reads. Set `OWNER_PRODUCTION_REPORTS_ENABLED` only after the ADR's data and privacy checks. Owner AI separately requires its production OpenAI credentials, non-shared report-reference secret, Worker rate limiter and credible freshness signal.

Build the production console with `VITE_PUBLIC_API_URL=https://api.peekaplate.app`; it emits the exact Pages rewrites for Overview, AI Insight Report, Dish performance, Menu, Actions and Restaurant Setup. Upload the generated `_redirects` with the build. Overview, AI Insight Report and Dish performance let owners refresh the authorized report. A failed refresh clears the prior report and lets the owner retry. Refresh does not change the report activation gate or privacy floor. The app verifies the session before accessing the protected workspace and preserves the existing onboarding requirements after sign-in.
